# Решения

Журнал решений там, где задание неоднозначно или где пришлось выбирать. Новые записи — сверху.

## Этап 3 — организации и роли

### Действия с правилами — серверные функции с машинными кодами ошибок

Создание организации, приглашения, вступление, заявки и смена ролей — функции `public.*`
(security definer), каждая сама проверяет права. Ошибки бросаются как `P0001` с кодом
(`invite_expired`, `last_admin`…); клиент переводит код через `errors.*` (`src/lib/db-errors.ts`).
Прямой INSERT в `org_invites` и `join_requests` клиенту запрещён.

### Приглашения

- Код — 96 случайных бит (16 символов base64url), подобрать перебором нельзя.
- Ссылка и QR одинаковые: `tazaniyet://join/<код>`; разбор принимает и полную ссылку, и сам код.
- Волонтёрская ссылка: неделя, без лимита. Координаторская: сутки, одно использование, создаёт
  только админ. Сразу админом пригласить нельзя — только назначить из участников.
- Вступление идемпотентно: повторное открытие ссылки участником ничего не меняет и не тратит
  использование. Исключение — приглашение координатора повышает уже вступившего волонтёра.
- Вступление по приглашению закрывает ожидающую заявку в ту же организацию.
- Ссылка, открытая до входа, запоминается и открывается сразу после входа.

### Заявки и поиск

Организации ищутся по названию или адресу (минимум 2 символа, до 20 результатов) — видны только
название, описание и число участников. Отдельный флаг «закрытая организация» пока не нужен:
вступление по заявке всё равно требует одобрения админа или координатора.

### Последний админ

Триггер не даёт понизить или удалить последнего админа организации — ни через функцию, ни прямым
запросом. Сначала нужно назначить другого.

### Имя обязательно перед вступлением

Вход по коду не спрашивает имя, а координатору нужно понимать, кто вступил. Поэтому перед
вступлением по приглашению и перед заявкой приложение просит имя, если оно пустое; изменить его
можно в профиле.

### Подтверждение опасных действий — повторным нажатием

Исключение участника, выход из организации и отзыв приглашения подтверждаются вторым нажатием
в течение 4 секунд. Это одинаково работает на телефоне и в вебе и удобно в перчатках.

### Кэш данных очищается при смене пользователя

Списки участников и приглашений кэшируются по организации, а не по пользователю, поэтому при
выходе или входе другим аккаунтом кэш TanStack Query полностью очищается.

### Доступность: `aria-*` вместо `accessibilityState`

`accessibilityState` в вебе не превращается в `aria-checked`/`aria-disabled` — экранный чтец не
узнавал выбранную роль. Компоненты используют `role` и `aria-*` свойства React Native, которые
работают на всех платформах.

## Этап 2 — база данных

### Локальный Supabase для разработки

Выбран пользователем. Миграции те же, облачный проект подключается позже через `supabase link`
и `supabase db push`. Seed предназначен только для локальной БД.

### Запись в доверенные таблицы — только сервер

Клиенту запрещены (на уровне привилегий, не только RLS) INSERT/UPDATE/DELETE в `quest_signups`,
`attendance_sessions`, `hour_confirmations`, `adjustments`, `points_ledger`, `audit_log`,
`certificates`, `user_skills`, `user_achievements`. Иначе RLS пришлось бы дублировать бизнес-правила
(лимит мест, QR, радиус, расчёт часов), и любая ошибка в политике позволила бы накрутить часы.
Запись появится как security definer функции / Edge Functions на этапах 4–7.

### Подтверждение часов — одно на волонтёра в квесте

`hour_confirmations` уникально по `(quest_id, user_id)`: координатор подтверждает итог по человеку
(сумму всех его смен в квесте), как в таблице подтверждения из задания. Смен у волонтёра в квесте
может быть несколько (ушёл и вернулся), но активная — только одна на человека вообще.

### Оценка — три оценки 1–5, множитель — по округлённому среднему

Задание называет критерии «качество, активность, командность» и один множитель баллов.
Храним три оценки; множитель берётся по `round(среднее)`. Баллы округляются до целого.
Окончательно формула выносится в конфиг на этапе 6.

### Неизменяемые журналы без `updated_at`

`points_ledger`, `audit_log`, `adjustments` — только добавление, UPDATE/DELETE/TRUNCATE запрещены
триггером даже владельцу БД. Колонка `updated_at` там не имеет смысла, поэтому её нет
(в остальных таблицах `created_at`/`updated_at` есть, `updated_at` ставит триггер).

### История важнее удаления

Внешние ключи из журналов (`points_ledger`, `hour_confirmations`, `adjustments`, `disputes`,
`audit_log`) — `on delete restrict`: организацию или пользователя с подтверждёнными часами нельзя
удалить физически, их нужно архивировать (появится на этапе 8). `audit_log.actor_id` без внешнего
ключа, чтобы запись аудита пережила удаление пользователя.

### Аудит пишется триггером

Изменения организаций, участников, задач, квестов, записей, смен, подтверждений, споров и
сертификатов попадают в `audit_log` автоматически (кто, действие, старое и новое значение).
Так аудит невозможно «забыть» в коде Edge Function.

### `org_id` денормализован в дочерних таблицах

В записях, сменах, подтверждениях, корректировках и спорах есть `org_id`, его всегда ставит
триггер (из квеста или подтверждения) — клиентское значение игнорируется. Это упрощает и ускоряет
RLS-проверки и делает невозможной подмену организации.

### Координаты — широта/долгота без PostGIS

Хватает для проверки радиуса (формула гаверсинуса на этапе 5) и не тянет лишнее расширение.

### Видимость

- Задачи «сверху» видят только админ и координаторы; волонтёры — квесты.
- Черновики квестов видят только админ и координаторы.
- Профили, навыки и достижения видны коллегам по общей организации.
- Аудит и споры организации видит админ; волонтёр — свои споры и все правки своих часов.
- Счётчик мест «7 / 15» для волонтёров появится на этапе 4 серверной функцией
  (сами записи других волонтёров им не видны).

## Этап 1 — каркас

### Хранилище сессии Supabase — expo-sqlite (`localStorage`)

Документация Expo SDK 58 рекомендует `expo-sqlite/localStorage/install` вместо AsyncStorage.
expo-sqlite всё равно нужен для офлайн-очереди (этап 5), поэтому лишней зависимости нет.
Минус: токены лежат не в Keychain/Keystore. Если понадобится усилить защиту — заменить адаптер
на expo-secure-store с шифрованием (сессия Supabase больше лимита SecureStore в 2 КБ).

### Вход — OTP по email или телефону, единое поле

Пользователь вводит email или телефон в одно поле; тип определяется автоматически
(`parseContact`). Телефоны нормализуются в E.164, казахстанские форматы `8 7xx…` → `+77xx…`.
Длина кода — 6 цифр (значение по умолчанию в Supabase). Повторная отправка — не чаще раза в 60 с.
SMS требует настроенного SMS-провайдера в Supabase (Twilio и т.п.); до этого работает вход по email.

### Защита маршрутов — `Stack.Protected` с явным `redirectTo`

Три состояния: онбординг не пройден → `/onboarding`; не вошёл → `/sign-in`; вошёл → вкладки.
`redirectTo` указан явно: по умолчанию роутер уводит на имя группы (`/(auth)`), которого нет как URL
(баг найден при ручной проверке в браузере).

### Язык

По умолчанию — первый поддерживаемый язык из системных локалей (kk/ru/en), иначе русский.
Пользователь может выбрать язык в профиле или вернуть «как в системе».
Эталонная локаль — `ru`; `kk` и `en` проверяются по ней типами и тестом.

### Палитра

Основной зелёный `#1B7A47`, бирюзовый акцент, солнечно-жёлтый для наград. Все пары текст/фон
и цвета сложности проходят WCAG AA (тест `contrast-test`). Тест сразу поймал два недочёта —
исходный цвет «Лёгкой» сложности и светлый фон primaryMuted были недостаточно контрастны.

### Без `.env` приложение запускается

Если переменные Supabase не заданы, клиент создаётся с заглушкой, а на экране входа видна
понятная ошибка. Так каркас можно открыть без бэкенда.

### Локальный Supabase — на этапе 2

`supabase/` (config.toml, миграции, seed) создаётся на этапе 2 вместе с БД. Сейчас подключение —
клиент, переменные окружения и поток авторизации.
